# AGENTS.md

Conventions for anyone (human or AI agent) working on this repository. See [README.md](README.md) for what the project does and how to build it.

## Target

- Board: **Raspberry Pi Pico 2 W** (RP2350A, ARM Cortex-M33). `PICO_BOARD=pico2_w`, `PICO_PLATFORM=rp2350-arm-s`. Do not add RP2040 (Pico, Pico W) support paths.
- SDK: official Raspberry Pi Pico SDK 2.3.1 via `PICO_SDK_PATH`, CMake + Ninja.
- Language: C++17 for firmware and tests, PIO assembly for `.pio` files.

## Architecture rules

1. **Pure core, thin hardware layer.** Any math (cycle counts, dividers, encodings, protocol bit streams) goes in `src/core/` with no Pico SDK includes, and gets host unit tests in `tests/`. Hardware modules in `src/hw/` (and later `src/protocols/`) call the core and program registers. They should contain as little logic as possible.
2. **No blocking delays for signals.** Signals are produced by PIO, PWM, DMA or hardware timers. The CPU main loop only runs the console. `sleep_ms` is acceptable in console code, never in signal generation.
3. **One place for pins.** `src/board_pins.h` owns every GPIO assignment. Changing a pin means updating `board_pins.h`, the pinout table in README.md, and the `bi_decl` lines in `main.cpp`.
4. **One place for defaults.** `src/signal_config.h` owns frequencies, duty cycles, patterns, preset content and PIO state machine allocation. Keep it SDK-free so tests can check it.
5. **Never use** GP23, GP24, GP25, GP29 (CYW43 wireless chip). Keep GP0/GP1 free of UART stdio (stdio is USB only). PIO2 belongs to the Wi-Fi driver, except SM0, which plays the GP26 bouncing button; keep every other signal in PIO0 and PIO1, so the driver always finds a free state machine and room for its program in PIO2.
6. **Peripheral conflicts:** PWM slices are shared by GPIO pairs (slice = (gpio / 2) % 8). Two signals with different frequencies must not share a slice. PIO state machines are claimed explicitly with `pio_sm_claim` so a double allocation panics at boot. `tests/test_config.cpp` checks pins and state machines for duplicates; extend it when adding outputs.
7. **Validate and report.** Every output computes its actual achieved timing, panics with a clear message on invalid config, and adds a row to the status table (`status_add`).
8. **Simple over clever.** Plain structs and free functions. Add an abstraction only when a second real user needs it.
9. **Signals before Wi-Fi.** Test signals are configured and started before the radio, and must keep running if Wi-Fi fails.
10. **One source of truth for the guide.** The web guide reads `web/src/data/signals.json`, `protocols.json`, `video.json` and `faults.json`, generated by `tools/export_signals.cpp`, `tools/export_protocols.cpp`, `tools/export_video.cpp` and `tools/export_faults.cpp` from the firmware's own config and encoders. Never edit the JSON by hand; regenerate it (`./build-tests/export_signals web/src/data/signals.json`, and likewise `export_protocols`, `export_video` and `export_faults`). A ctest check fails when any is stale.
11. **Captive portal rules.** The hotspot address must not be private (no 192.168.x.x, 10.x or 172.16-31.x): recent Android treats a connectivity check resolving to a private address as "no internet". On the hotspot only `/guide` serves the page; every other non-API URL, `/` included, must redirect to it, because phones probe different paths (see `src/net/http_server.h`). The DHCP server and catch-all DNS run only in setup (hotspot) mode, never on a home network. Use `-DLTB_NET_DEBUG=ON` to see what a phone actually sends.
12. **Saved settings.** The saved network and the signal preset live in the second-to-last 4 KB flash sector (`src/hw/settings_store.cpp`, layout in `src/core/settings.h`); never the last one, which every RP2350 `.uf2` erases (erratum E10 workaround block). Bump the layout version if you change the layout, and keep loading the previous version (as layout 2 loads layout 1) so an update never forgets the network. Never return the saved password from any API or console command. Flash writes and reboots happen in `wifi_poll()` or `preset_poll()` (main loop), never in lwIP callbacks, which run in interrupt context.
13. **Web API.** Routes are listed in `src/net/http_server.h`; keep `web/src/model/device.ts` and the dev mock (`web/dev/mockDevice.ts`) in sync with them.
14. **Signal presets.** GP10-GP22 play one preset at a time (`src/core/presets.h`), one frame builder per preset (`src/core/protocol_frame.*`, `src/core/video_frame.*`, `src/core/faults_frame.*`) on the same timeline state machine. GP0-GP9 and GP26 never change with the preset. The preset is read at boot before any signal starts; switching saves it and restarts the board, so all signals start in sync. Preset numbers are stored in flash: never renumber them.

## Web guide (web/)

- Preact + TypeScript + Vite, built into one self-contained `index.html` (vite-plugin-singlefile) that the firmware embeds. Keep it small (currently about 90 KB gzipped) and fully offline: no CDN scripts, no web fonts, no external requests.
- Lessons are data, one file per lesson in `web/src/lessons/concepts/`, `basics/`, `protocols/`, `video/`, `faults/` or `verify/`, each exporting one `Lesson`. A lesson teaches with explanation `sections`, hands-on `parts` (captures with settings and expected waveforms), or both; one without parts wires no pins. Shared building blocks (wiring steps, example views, byte helpers) are in `web/src/lessons/helpers.ts`, the shapes in `types.ts`. `web/src/lessons/index.ts` lists the lessons in guide order; a new lesson is a new file plus one line there. Compute every number from the signal data; never type expected values by hand.
- **Analyzer neutral.** The guide is for any logic analyzer and any software. Never name an app's menus or buttons, never number analyzer channels: refer to signals by Pico pin (`GP10`) and say "any free input". Describe settings in plain terms (sample rate, length, trigger edge on a pin, decoder parameters).
- A lesson only some readers can follow (it needs a software feature not every analyzer app has, such as sigrok decoders) sets `optional` to a sentence saying who can skip it. The page and the lesson list mark it, and a test checks that no other lesson relies on it.
- Readers can mark lessons as done (`web/src/model/progress.ts`). The marks live in the browser's localStorage only, guarded so the guide works without it.
- A lesson with `mystery: true` hides what its pins carry (wiring, labels, trigger text) and shows no waveforms; its answers go in the questions, which are collapsed.
- A lesson that wires GP10-GP22 names its `preset` (default `protocols`); it shows a switch banner when the board plays another one. The lesson tests check that it only wires pins its preset drives.
- Every lesson must work on a small analyzer: at most 8 inputs and 24 MS/s per capture (`web/src/model/capture.ts`). The lesson tests enforce it.
- `npm --prefix web test` must pass. It checks that every lesson's settings are accepted by the analyzer and that its views fit the capture window.
- Hash routing only (`#/lesson/<id>`), so the page works from the Pico, a file, or any static host.

## Adding a protocol

Protocols live on the timeline (GP10-GP22, one PIO state machine, 120 ms frame); they do not get their own state machine or driver.

1. Write an encoder in `src/core/protocols/<name>.{h,cpp}` that writes edges into `wave::PinWave`s (`src/core/wave.h`) in clk_sys cycles. Simulate both sides of the bus. Place edges per bit from the transaction start so timing never drifts. Add tests to `tests/test_protocols.cpp` that decode the waveform the way an analyzer would.
2. Add its settings to `config::ProtocolConfig` in `signal_config.h`, its pins to `board_pins.h` (the timeline is one contiguous block of at most 13 pins), and a slot in `src/core/protocol_frame.cpp` (record a `Window` for each transaction). Raise `kPinCapacity` if needed.
3. Add a status row in `src/hw/timeline_output.cpp`, an export in `tools/export_protocols.cpp` (facts plus one example window), then regenerate `web/src/data/protocols.json`.
4. Write the lesson as `web/src/lessons/protocols/<name>.ts`, add it to `web/src/lessons/index.ts`, and update README (signals table) and docs/timing.md (precision).

All 13 timeline pins are in use in the Protocols preset, so a new protocol needs a pin freed first, or goes into another preset. Signals that cannot share the 120 ms frame get a preset of their own: a frame builder like `src/core/video_frame.cpp`, a case in `src/hw/timeline_output.cpp`, an exporter, and lessons with that `preset`. The Video and input preset leaves GP20-GP22 free, the Faults preset GP21-GP22. GP27 and GP28 are the only other free pins. A fault for the Faults preset is an option on an existing encoder (defaulted, so the Protocols preset is unchanged) plus a slot in `src/core/faults_frame.cpp`, a test in `tests/test_faults.cpp` that decodes it, an export, and a lesson in `web/src/lessons/faults/`.

## Build and test before committing

```bash
cmake -S tests -B build-tests && cmake --build build-tests && ctest --test-dir build-tests --output-on-failure
```

```bash
npm --prefix web test
```

```bash
cmake -S . -B build -G Ninja && cmake --build build
```

All three must pass, and the firmware build must produce **no warnings** from files in `src/` (`-Wall -Wextra` is on for our sources). Hardware behavior cannot be verified without a board and analyzer; say so explicitly when a change is untested on hardware.

## Code style

- 4-space indent, 120 column limit, braces on the same line.
- `snake_case` functions and variables, `PascalCase` types, `kConstantName` constants, namespaces for grouping (`timing::`, `config::`, `pins::`).
- Comments explain **why** and the hardware facts behind a choice (cycle counts, register quirks, datasheet constraints). Every `.pio` file documents its exact cycle timing. Do not narrate obvious code.
- Fixed-size static buffers, no heap allocation in firmware.

## Documentation

- Keep README.md (end-user facing) and docs/timing.md current with every user-visible change: pins, defaults, limits, commands.
- American English spelling ("color", "behavior", "initialize").
- Never use the em dash character. Use a comma, a colon, or a plain hyphen.

## Commits

- Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, `build:`. If tied to a ticket, prefix with the ticket number instead (`ABC-12: ...`).
- Short imperative subject line, blank line, then a body explaining what changed and why.
- No `Co-Authored-By` or other attribution trailers.
- Version follows SemVer in `pico_set_program_version` (CMakeLists.txt): bump minor for new modes or signals, patch for fixes.

## Releases

Pushing a tag `vX.Y.Z` makes CI (`.github/workflows/ci.yml`) build and test everything, then publish a GitHub release with `logic_test_bench.uf2` and `logic_test_bench-net-debug.uf2` attached. The README's download links point at the latest release, so it must always contain a working `.uf2`.

1. Bump `pico_set_program_version` in CMakeLists.txt and merge to `main`. The release job fails if the tag and this version differ.
2. Tag the merge commit on `main` and push the tag: `git tag v0.4.0 && git push origin v0.4.0`.
3. A tag with a suffix (`v0.5.0-rc1`, same suffix in CMakeLists.txt) is published as a prerelease, which the "latest release" links skip.
